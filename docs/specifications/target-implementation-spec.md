# Target Implementation Spec

本文档记录用户已确认的长期目标态。当前已实现的系统状态见 `docs/current-architecture.md`；只有用户明确确认的目标才写入本文档。

## 北极星

把 Knowledge Vault 打造成一个服务个人研究与知识工作的长期系统，而不是只做一个"文献管理器"。

## 前端技术基础（2026-09-05 确认）

- 长期前端框架采用 React + TypeScript + Vite，不使用 Vue 或 Next.js。
- 路由与服务端状态分别采用 TanStack Router、TanStack Query；表单采用 React Hook Form + Zod；HTTP 继续通过 Axios 对接独立 Flask API。
- UI 采用 Tailwind CSS 4 与可维护的源码组件，保留 ECharts；质量体系包含 ESLint、Prettier、Vitest / React Testing Library 和 Playwright。
- 保持前后端分离、浏览器 URL、桌面托盘启动方式和动态端口编排，前端技术演进不主动改变 Flask API 合同。
- 普通笔记继续使用文本输入；只有明确出现富文本编辑需求时再评估 TipTap，不把编辑器复杂度预先引入基础架构。

## 论文与采集体系（2026-08-30 确认）

### T-1 采集源可配置

- 目前支持的采集方式：按期刊批量采集，采集内容为题录数据（标题、摘要、作者等）。
- 现有采集源：国内期刊可走国家哲学社会科学文献中心或已配置的 Magtech 官网；国外期刊题录主源为 Scopus Search API，按期刊 ISSN + 年采集；原 Elsevier 浏览器源保留为可选兼容源。
- 目标：按期刊批量采集时可以选择采集源。国内期刊候选源包括国家哲学社会科学文献中心、知网、期刊官网；每个期刊采集时从该期刊当前支持的源中选择一个执行。
- 已落地的能力范围（采集源注册表、期刊级源配置、官网源）见 `docs/current-architecture.md` 的「采集源与期刊配置」。
- Scopus 按 ISSN + 年查询后按论文真实卷期保存独立采集批次；同一期号跨卷不得合并，缺卷/缺期进入明确的未知卷或未分期批次。国外全文能力仍受 T-2 的授权与访问控制约束。

### T-2 采集全文 PDF

- 采集流程支持下载论文全文 PDF，与统一文献关联保存；PDF 是文献资产，不属于某个 raw_issue 的派生产物。
- 支持文献详情单篇获取、采集期号批量补采、题录完成后可选自动补采三种入口；题录与全文后台保持独立阶段，全文失败不回滚题录。
- 批量任务只处理缺失 PDF 的文献；用户上传 PDF 不被自动采集覆盖；单篇重新获取只替换当前同来源的官网 PDF。
- 删除或重采来源期号时保留 PDF 和来源快照，只清空已经失效的 raw_paper 引用。
- 当前实现范围包括国内 Magtech 官网和可由 Scopus PII 定位的 ScienceDirect 论文；ScienceDirect 仅使用用户已有的机构授权，不绕过登录、付费墙、验证码或访问控制。人机校验和网络出口限制必须暂停任务并允许人工处理后续跑，订阅不足按单篇失败记录。

### T-3 单篇论文题录采集（待定）

- 是否支持单篇论文的在线题录采集功能待定；T-2 已实现对现有统一文献单篇补采 Magtech PDF，但不新增或补采题录。架构设计需保持单篇题录采集可以低成本加入。

### T-4 采集数据与文献工作台打通

- 目标：采集到的论文信息与文献工作台中的论文信息打通，不再是两套隔离数据。
- 论文的两条获取途径：期刊批量采集、手动导入；两种来源最终进入统一的论文体系。
- 允许论文只有题录数据而没有 PDF。
- 同一文献可关联多个采集来源；匹配时 DOI 优先，否则使用清洗标题及期刊、年份、期号共同判断。
- 统一文献按字段物化，优先级为用户编辑、期刊官网（Magtech）、国家哲社文献中心、其他来源；高优先级来源字段为空时由下一来源补位。
- 用户手动编辑的字段不再被自动采集覆盖。删除某个采集期号后，从剩余来源重新计算字段；删除最后一个来源时保留文献、笔记、标签、文件夹和 PDF。
- 官网标题只清除严格成对且正确嵌套的 `bold`、`italic`、`sup`、`sub` 标签；异常标签结构保留原文并记录 warning。

### T-5 文献管理能力增强

- 文献管理目前缺少按期刊筛选，后续补充该能力（隐含：期刊需要成为一等实体）。

## 大模型能力（2026-08-30 确认）

### T-6 分析场景平台化

- 大模型调用是论文分析、论文翻译和视频笔记共享的平台能力，不属于单一业务模块的内部实现；后续场景继续复用统一调用接口。
- 论文分析作为独立工作台能力，支持按单期、多期或多篇统一文献选择；采集与手工导入论文使用同一分析流程。
- 大批论文需要分批处理并综合结果，任务应异步执行并保留输入快照、运行状态与历史结果。
- 整期分析自动包含所选卷期全部论文，与自选论文模式互斥；自选论文可综合检索整个统一文献库、分页浏览并跨页保留选择；默认 Prompt 对用户可见，自定义要求在默认 Prompt 基础上追加。
- 分析可选使用已有 PDF 全文；PDF 转 Markdown 结果按 PDF 内容哈希与解析管道版本复用，记录实际解析器版本和内容哈希，分析历史引用所用文本资产而不复制整份 Markdown。

### T-7 多模型供应商支持

- 大模型不限定 Gemini，应支持配置多个供应商的 `base_url`、`model_name`、`api_key` 等信息；每个用户主动发起的大模型任务必须选择具体模型档案，并保存实际模型快照。
- Gemini 使用原生协议，其他供应商统一按 OpenAI Compatible 协议接入；场景名称只用于 Prompt 与调用类型分类，不维护场景默认模型。
- API Key 只保存在本机忽略文件中，不进入随仓库提交的数据库，也不通过 API 回传。
- 采集服务密钥与大模型档案分属不同配置入口，避免把数据源凭据误解为模型配置。

## 架构方向（2026-08-30 确认）

- 功能模块化：不按"三大域"粗粒度切分，域内部继续拆分为可独立维护、修改、复用的子模块；采集本身也由多个模块化能力组成（源适配、题录解析、PDF 下载、入库合并等）。
- 视频转笔记保持独立域；未来可能与其他功能打通，也可能新增独立功能或交叉功能，架构需为持续演进预留空间，随功能增加持续评估更合适的结构。

## 近期目标（2026-08-30 确认）

### 1. 稳定采集链路

- 提高国内/国外期刊采集的稳定性
- 明确原始数据、翻译、分析之间的状态流转
- 降低依赖脚本式人工处理的环节

### 2. 完善知识整理能力

- 把采集结果更自然地接入文献条目、标签、文件夹和笔记
- 为后续知识沉淀打基础

### 3. 拓展多源内容输入

- 让视频内容进入统一工作台
- 稳定"链接 -> 字幕 -> 笔记"的自动化流程
- 为后续更多媒体来源打基础

## 中期方向（方向性目标，2026-08-30 确认）

- 支持更多知识来源的采集与导入
- 引入更完整的知识整理与关联能力
- 增强摘要、分析、比较、再利用等 AI 工作流
- 逐步形成"采集 -> 整理 -> 沉淀 -> 输出"的闭环

## 暂不追求（负面约束，2026-08-30 确认）

- 为了堆功能而增加彼此割裂的新子项目
- 在没有文档和结构约束的情况下快速扩张
- 只围绕"文献"单一对象设计整个系统
